# Ask-Plan — 规格驱动的契约化增量规划

本手册是 `dumb-coding` 技能的第 2 子阶段（`ask-plan`：契约化增量规划层），严格承接 `ask` 子阶段（[ask.md](./ask.md)）产出的已批准设计规格（Spec），并在编码实现前锁死工程蓝图。

**核心假设**：接手执行这份计划的人（全新上下文的子代理或下一阶段的实现工程师）精通项目语言与测试惯用法，但**完全没有看过前序需求讨论**。只要给出精确的文件边界、函数签名与测试断言，他们就能写出地道的业务实现；他们唯一不可能凭空知道的，是你做出的**工程拆解决策**——改哪几个真实文件、暴露什么精确名称与类型、Spec 钉死了哪些常量/错误码、相邻任务靠什么契约衔接、哪条命令证明任务通过。

**计划就是（且仅是）实现者无法独自做出的那组精确工程决策。** 遵循 DRY、YAGNI、TDD 与小步可验证增量原则。

**启动声明**：开篇用一句话告知用户正在执行 `dumb-coding` 的 `ask-plan` 阶段，基于指定 Spec 构建增量实施计划。

---

## 0. 准入硬门禁：无已确认 Spec，绝不写 Plan

<HARD-GATE>
ask-plan 阶段必须以一份经用户确认锁定的设计规格（Spec）作为唯一合法输入。

启动第一步必须核验目标 Spec（默认位于 docs/specs/YYYY-MM-DD-<topic>-design.md）：
1. 文件真实存在，且处于已获用户确认的状态（文档头部标记为“已批准”，或用户在当前请求中明确指定确认以该份 Spec 为准）。
2. 若不存在书面 Spec、Spec 仍处于未对齐的草稿态，或用户跳过前置对齐直接抛出模糊需求要求出计划——必须立即中止 ask-plan，明确说明缺少已确认的 Spec 基线，并引导先通过 ask 阶段（[ask.md](./ask.md)）完成事实接地与规格审批。严禁拿零散对话摘要硬充当 Spec 直接拼凑计划。
</HARD-GATE>

若通读已批准 Spec 后，发现仍存在极个别足以改变任务拆解走向的真实缺口，先通过结构化提问工具（`ask_question` / `AskUserQuestion`）做最小化澄清并同步回 Spec，再动笔编写 Plan。

## 1. 实现层二次事实接地（Implementation Grounding）

Spec 锁定的是架构与行为边界，动笔拆解任务前，必须深入代码库核实所有**实现级事实**，彻底消除规划幻觉：

1. **真实符号与路径核验**：若仓库存在 `.codegraph/` 且 `codegraph_explore` 可用，优先用其确认待改动函数/类的精确定义位置、现有签名与全部调用方；结合 `read` / `grep` 核对目标文件的真实路径、行号区间与周边错误处理风格。
2. **工具链与验证命令核验**：确认项目真实的单测运行命令（如 `pnpm exec vitest run <test-file>`）、类型检查命令、构建脚本及第三方库在锁文件中的实际版本（必要时用 Context7 或最小探针确认 API 细节）。
3. **版本控制与目录约束核验**：检查一次当前工程是否为 Git 仓库，以及计划保存路径（默认 `docs/plans/YYYY-MM-DD-<feature-name>.md`，用户偏好优先）或构建产物路径是否受 `.gitignore` 与仓库提交规范约束。
   - **Git 仓库**：每个任务末尾包含精确暂存关联文件的提交步骤；
   - **非 Git 仓库**：计划全文严禁出现任何 `git` 提交步骤。

**接地铁律**：绝不允许在 Plan 中写出未经核对的假想文件路径、不存在的既有接口名或未经验证的命令行参数。

## 2. 范围校验与文件职责映射（Scope & File Mapping）

### 独立子系统拆分检查
若输入的 Spec 实际上横跨多个彼此独立的子系统，应先向用户建议按子系统拆分为多份顺序推进的实施计划——**每一份 Plan 独立执行完毕后，都必须产出可编译、可测试、可运行的完备软件增量**。

### 先锁文件边界，再拆增量任务
在定义任何 Task 前，先在脑中（及计划架构段）排定所有新建与修改文件的职责映射：
- **单一职责与高内聚**：每个文件只承担一项清晰职责；会一起修改的代码放在一起，按业务职责而非机械的技术分层切分；优先小而聚焦的文件，使单任务执行者能一次读入完整上下文并可靠编辑。
- **尊重既有代码库惯例**：在存量项目中沿用既有的目录与命名风格，不擅自搞全仓大重构；仅当待修改文件本身已严重膨胀失控时，才将局部文件拆分纳入具体任务步骤。

## 3. 任务定界与无歧义步骤准则（Task Sizing & Step Discipline）

### Task 粒度定界（Right-Sizing）
一个 Task 是**自带完整测试闭环、且值得一次独立代码审查门禁的最小交付单元**：
- 将初始化配置、脚手架、共享类型声明与关联文档更新并入真正消费它们的业务交付任务中，不为凑数拆出无法独立验证的空壳任务；
- 仅在独立审查者有可能“批准前一个任务、但有意义地驳回后一个任务”的自然契约边界处拆分；
- 每个 Task 结束时都必须留下可独立运行测试验证的干净状态。

### 跨任务契约隔离（`Interfaces` 块）
假设每个 Task 的实现者**只能看到计划头部与自己负责的那一个 Task**：
- 每个 Task 必须显式列出 `Consumes`（消费前序任务或既有模块的精确导入路径与签名）与 `Produces`（向后序任务承诺暴露的精确函数/类名、参数类型与返回类型）；
- 后序任务直接通过前序任务的 `Produces` 契约衔接，不在正文中重复粘贴前序任务代码。

### TDD 原子步骤与“不多不少”无歧义标准
每个步骤是清晰的**单一动作 + 可检验预期结果**（写失败测试 → 跑测试确认按预期原因失败 → 写最小实现 → 跑测试确认通过 → Git 提交）；执行阶段使用宿主原生任务列表追踪进度，Plan 原文保持只读。

判断一个步骤是否合格的唯一标准：**实现者据此只能写出唯一合理的代码，既无需瞎猜，也未被越俎代庖。**
- **测试步骤**：给出测试名称与断言代码，将 Spec 钉死的精确输入、阈值、状态码与错误码直接写进断言。
- **实现步骤**：给出精确目标文件路径、完整导出签名（名称、参数、返回类型）与 Spec 锁定的业务常量。**函数体留给实现者编写**——仅当签名与测试断言仍无法唯一确定复杂算法、状态机转移或固定文案时，才附上最小必要代码片段。
- **验证步骤**：给出精确可执行的命令及代表通过的预期输出。

## 4. 编写计划与六维自审（Write & Self-Review）

动笔前读取 [plan-template.md](./plan-template.md)，严格按照其中的文档头部（含 `Execution Mode`、`Global Constraints` 与 `Review Focus`）及 `Task N` 结构编写完整计划，并保存至 `docs/plans/YYYY-MM-DD-<feature-name>.md`。

落盘后，立即切换审视视角，**亲自对照原 Spec 执行以下六维自审清单**（无需派发子代理；发现问题当场原地修正）：

1. **规格覆盖率（Spec Coverage）**：逐节对照 Spec 的目标、非目标、反目标与已锁定契约——每一项要求是否都能指认到具体落地的 Task？若有遗漏，立即补齐任务或步骤。
2. **步骤双向排雷（Step Scan）**：
   - *查缺口*：全文是否存在无决策空话（如 `TBD`、“处理边界情况”、“补充适当参数校验”、“为上述逻辑补测试”、或引用了任何任务都未定义的类型/函数）？全部替换为精确决策。
   - *砍冗余*：是否把签名+测试早已唯一决定的普通函数体大段抄进了计划？删去实现抄本，收敛为精确签名与断言。
3. **跨任务类型与命名一致性（Interface Consistency）**：Task 7 `Consumes` 的函数名、字段名、可选性与返回类型，是否与 Task 3 `Produces` 的声明逐字吻合？（例如前文叫 `clearLayers()`、后文写成 `clearFullLayers()` 即为规划缺陷。）
4. **隐含失效模式钉死（Review Focus Pinning）**：Spec 往往只写软件“应该做什么”，而沉默不代表允许异常输入弄崩系统。检查顶部 `Review Focus` 是否提炼了 Spec 未明写但真实运行最易踩坑的 5 类边界输入/并发/故障模式（若全面核查后确少于 5 条或无遗漏，须显式写明核查结论，不得留空跳过）：
   - **纯工程健壮性防御**（空值、越界、并发竞态、资源释放等）须在归属 Task 中补齐对应的钉死测试步骤与断言；
   - **涉及产品行为语义空白**（例如重复提交应静默幂等还是返回错误）不得擅自写死进断言，须先按第 0 节做最小澄清回补 Spec，或在 Plan 审批时高亮标注请用户拍板。
5. **篇幅比例审视（Proportion）**：对比 Plan 与 Spec 的体量。若 Plan 篇幅达到 Spec 的数倍且大部分篇幅是业务源码块，说明你写的是代码抄本而非计划——提炼契约、精简代码块并复核无歧义性。
6. **版本控制与仓库卫生（VCS Hygiene）**：确认 Git 提交步骤与仓库状态一致（非 Git 仓库零 `git` 字样；Git 仓库严禁 `git add -A` / `git commit -a`，不暂存被 `.gitignore` 忽略的文件）。

## 5. 出口硬门禁与分层执行交接（Exit Gate & Handoff）

自审修补完毕后，若符合仓库规范需提交计划文档本身可按规处理（注意避开本地忽略规则），随后在回复中附上 Plan 文件链接，并按 [plan-template.md](./plan-template.md) 中的交接话术，通过结构化提问工具（`ask_question` / `AskUserQuestion`）请求用户审阅批准计划、确认后续执行模式：

- **子代理逐任务隔离驱动（Subagent-driven）**：未来执行阶段每推进一个 Task，派发全新上下文的 Implementer 子代理编码，再派发全新 Reviewer 子代理对照 `Interfaces` 与 `Global Constraints` 独立审查，修完问题再进下一 Task，最后做全量规格终审。隔离最彻底、返工率最低，适合多任务耦合或高可靠性要求场景。
- **当前会话按步原生执行（Native + 独立终审）**：未来执行阶段在单会话内配合宿主原生任务列表按步顺序执行并验证，全部完成后派发一个高能力模型的全新 Reviewer 子代理对照 Spec 与 `Review Focus` 做全量独立终审。速度最快、上下文开销低，适合任务数少、接口直白的中小型计划。

用户批准 Plan 并选定执行模式后，**仅一次性**将 Plan 头部状态更新为 `已批准（YYYY-MM-DD）` 并在 `Execution Mode` 区块写入所选模式对应的精简执行与终审纪律（此后 Plan 作为只读蓝图不再修改），随后立即结束 `ask-plan` 阶段，等待用户在当前会话或新会话中发起执行指令。

<HARD-GATE>
在用户明确审阅批准实施计划（Plan）之前，严禁触碰任何业务源码或正式测试文件。

严格分层隔离规划与实现：用户批准 Plan（并一次性锁定头部状态与 Execution Mode）即标志着 ask-plan 阶段彻底结束。本阶段的终点是交付经用户确认锁定的增量工程蓝图与执行协议——绝不允许在本阶段内部顺手启动业务代码编写循环。实际代码实现必须由用户在下一条明确指令中开启。
</HARD-GATE>

## 常见反模式对照表（Red Flags）

| 危险念头 | 事实纠偏 |
| :--- | :--- |
| “虽然还没有 Spec，但对话里聊得差不多了，我直接写 Plan” | 触犯准入硬门禁：无用户确认锁定的 Spec 严禁写 Plan，立即退回 `ask` 阶段。 |
| “这个目录结构我猜大概长这样，直接写进 Files 吧” | 规划前必须用 CodeGraph / `read` 核实真实路径与现有签名，严禁把幻觉写进蓝图。 |
| “我把每个函数的完整实现代码都贴进 Plan，执行者照抄就行” | 比源码还长的计划是代码抄本；锁死签名、常量与测试断言，把函数体留给实现者。 |
| “步骤里写一句‘补充适当的边界与错误处理’就够了” | 实现者各猜各的就会返工；把真正要防的边界写进 `Review Focus` 并转化为具体测试断言。 |
| “Task 1 建空目录配环境，Task 2 写类型文件，Task 3 再写逻辑与测试” | 拒绝无独立测试闭环的碎片任务；配置与类型随首个可测试业务增量一起交付。 |
| “Plan 写完用户刚点批准，我现在就开始写 Task 1 代码” | 规划与实现严格分层隔离；批准 Plan 并锁定执行协议即结束 `ask-plan` 阶段，等用户下一条指令再动工。 |
