# Spec 标准模板与 Builder Check 盲审规程

本文档供 `dumb-coding` 技能的 `ask` 子阶段（[ask.md](./ask.md)）在编写设计规格（Spec）及执行完整工程独立复核（Builder Check）时按需读取。

---

## 1. 设计规格（Spec）标准模板

编写的 Spec 应当让一位熟悉该领域但**从未参与前序对话**的工程师，无需再回头追问用户即可据此制定出严密的增量实施计划（`ask-plan`）。

> **门禁状态契约**：初稿落盘时状态填为 `待批准（YYYY-MM-DD）`；仅在用户通过结构化提问工具明确批准后，更新为 `已批准（YYYY-MM-DD）`。下游 `ask-plan` 子阶段（[ask-plan.md](./ask-plan.md)）依赖该状态校验准入门禁。

```markdown
# [特性 / 模块名称] 设计规格

- **状态**：待批准 | 已批准（YYYY-MM-DD）
- **日期**：YYYY-MM-DD
- **涉及范围**：[受影响的子系统、模块或核心目录]

## 1. 意图与背景（Intent & Why）

[用平实清晰的语言说明要解决什么真实问题、服务什么场景、为什么现在做，以及当前代码库的相关现状基线。]

## 2. 目标、非目标与反目标

### 2.1 目标（Goals）
- [可验证的核心交付结果与成功判据]

### 2.2 非目标（Non-Goals）
- [本轮明确不做、留待后续或交由其他机制处理的范围]

### 2.3 反目标（Anti-Goals）
- [即便功能表面跑通也绝对不允许触碰的工程红线，例如：引入第二套事实源、破坏工作区隔离、暴露敏感凭据、破坏向后兼容等]

## 3. 事实基线与硬约束（Grounded Facts & Constraints）

- **现有代码契约**：[调研确认的关键调用链、存储结构、生命周期或配置基线]
- **技术与依赖约束**：[运行时版本下限、锁文件已确认的依赖版本、零新增依赖或性能/安全硬指标]

## 4. 方案比选记录（Approaches）

| 候选方案 | 核心机制与改动面 | 权衡（收益 vs 代价） | 结论 |
| :--- | :--- | :--- | :--- |
| **方案 A（已选）** | [简述机制] | [收益与代价] | **采用**：[选定原因] |
| **方案 B** | [简述机制] | [收益与代价] | 放弃：[淘汰原因] |

## 5. 已锁定的设计契约（Decided Design）

[按模块、数据模型、状态流转、接口边界、异常/降级语义写清用户已拍板与对齐的核心设计。涉及界面、状态机或复杂结构时附上紧凑的图表或文本草图。只锁定架构与行为契约，不在此处堆砌具体任务步骤或完整实现代码。]

## 6. 工程默认取舍与规划自由度（Builder Calls & Open Latitude）

- **已声明的工程默认取舍**：[列出对话中由 Agent 提出默认并报备、非用户主动钦定的技术决定，便于用户审阅时集中核对]
- **留给规划/实现者的自由度**：[明确哪些内部实现细节交由后续 `ask-plan` 与编码阶段自行裁量]
```

## 2. Builder Check 独立构建者盲审提示词

对于定级为**完整工程（Project）**的任务，在 Spec 初稿落盘后、正式呈交用户审批前，派发一个**全新的只读/通用子代理**运行下方提示词（填入具体领域与 Spec 绝对路径）。告知用户你正在对规格初稿做一轮构建者盲审，最多可能带回一轮补充确认。

若当前宿主环境无子代理能力，请清空预设心理，严格以“第一次读到这份文档的外部实现工程师”视角自行执行同等检查。

```text
你是一位经验丰富的软件系统工程师（领域：[填入具体技术领域，如 "TypeScript 插件与存储引擎开发"]）。
你刚刚接手了一份设计规格文档（Spec），任务是接下来独立编写增量实施计划并交付代码，且在此过程中你将无法再向原作者提问。

请阅读设计规格文档：[填入 SPEC 绝对路径]，并按需核对仓库中的真实关联源码。

请仅报告那些“在制定可靠实施计划前必须先得到明确答案”的关键缺口——即文档留白迫使你不得不靠猜、且一旦猜错就会导致返工、破坏现有契约或偏离意图的分歧点（例如：未定义的错误/并发/空值边界行为、与仓库现有代码的真实接口冲突、缺失的数据迁移或安全隔离规则）。

对每一条问题，请给出：
1. 具体问题是什么；
2. 它源自文档哪一处留白或与哪段现有代码冲突；
3. 不同的答案会如何实质性改变后续实施计划。

请按严重程度从高到低排序。
跳过以下内容：
- 文档已在“留给规划/实现者的自由度”中明确放权的部分；
- 合格工程师可凭常规惯例自行妥善决定的局部实现细节；
- 纯粹的措辞润色或排版挑刺。

如果不存在任何会导致返工的关键缺口，请直接回复：“无关键规划缺口（nothing important left）”。
```
