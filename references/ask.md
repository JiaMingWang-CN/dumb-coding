# Ask — 事实接地与需求规格对齐

本手册是 `dumb-coding` 技能的第 1 子阶段（`ask`：前置对齐与规格锁定层）。

AI 极擅长快速构建“自己以为用户想要的东西”，但这种预设往往比感觉上单薄得多；而人在提出需求时，也常常尚未推演完所有边界。本阶段通过**前置事实接地消除幻觉、苏格拉底式单步追问对齐意图、强门禁锁定设计规格（Spec）**，确保在进入 `ask-plan` 阶段（[ask-plan.md](./ask-plan.md)）或编写任何业务代码前，把“做什么（What）”与“为什么（Why）”彻底锚定。

---

## 0. 分流判定：现在究竟知道多少？

回复前先自问：关于用户真正想要什么、为什么做、触及哪些现有系统边界，事实是否已经完备？

- **意图与实现均零歧义的局部微调**（例如“把某处文案拼写改对”“将图标改为 `#6495ED`”）：不属于本流程范围，直接完成并简要说明。
- **存在任何影响系统行为、范围或架构选型的未决项**：启动本阶段流程。在进入任何规划或实现前，必须严格按序完成：
  1. **代码库与依赖事实接地**（先查事实，绝不盲问）；
  2. **单步追问与渐进复述**（摸清真实意图与边界）；
  3. **独立呈现方案比选并获用户拍板**；
  4. **编写分级设计规格（Spec）并获用户明确审批锁定**。

若首轮事实调研后发现需求已完全自洽、不存在实质分歧且仅有一条合理的工程路径，可在首条回复中合并给出精简方案与轻量规格草案，直接发起审批。

---

## 1. 事实接地：先查代码，再开口提问（Ground Before Asking）

在发出第一条回复前，必须先对当前仓库及上下文做深度调研，直到你能清楚说明**相关模块目前如何工作**以及**本次改动会触及哪些真实边界**：

1. **代码结构与调用链核验**：若仓库根目录存在 `.codegraph/` 且 `codegraph_explore` 可用，优先用其定位符号定义、上下游调用链与影响面；结合 `read` / `grep` 核对相关源码、配置文件与现有测试契约。
2. **第三方库与宿主 API 核验**：涉及外部库、框架、SDK 或宿主插件协议时，先查锁文件确认实际安装版本，再通过 Context7 文档检索或最小本地探针核实接口签名，**严禁凭记忆臆造 API 或配置项**。
3. **既有上下文承接**：通读用户指出的文件、既有 Spec / Plan、Issue 或前序讨论。

**接地铁律**：
- 仓库源码、配置文件或既有上下文已经能回答的事实，**绝不允许反过来问用户**。
- 用户已经明确拍板的决定，**绝不无故翻案重问**；唯独当代码事实揭示了用户未曾留意的硬冲突、安全/隔离隐患或成本低得多的现成路径时，必须摆出事实直陈利弊。

---

## 2. 结构化单步提问契约（Structured Questioning）

所有需要用户作答、纠偏或审批的节点，必须调用宿主的**结构化提问工具**（如 `ask_question` / `AskUserQuestion`），**严禁在纯文本末尾抛问题干等回复**。

- **每次只问一题**：对齐阶段每次调用只放一个问题（仅最终 Builder Check 汇总残余分歧时例外），让下一问精确建立在上一答的反馈之上。
- **题干必须自包含**：用户可能只看提问卡片而不看前文。题干中须用 1–2 句话写清：**你从代码中查到了什么事实、为什么要问这一题、不同选择会改变什么构建结果**。
- **先开放探意图，再具象给选项**：
  - 在摸清用户**为什么（Why）**要做之前，提开放式问题（提示用户可在“其他 / Other”中用自己的话描述，选项仅列宽泛方向，避免用预设菜单诱导或限制用户思路）。
  - 一旦明确了意图且决策点存在可命名的具体路径：把你的推荐项放在首位并标注 `(Recommended)`，写明各选项的收益与代价（Trade-offs）。若各选项的界面布局、目录形态、数据流或接口长相不同，在消息中附上几行紧凑的**文本草图（ASCII / 签名轮廓）**辅助直观对比。
- **分清决策归属**：
  - **产品行为、需求范围、数据安全/隐私隔离与破坏性动作** → 必须问用户；
  - **纯工程过程决策**（继续查哪些文件、内部辅助结构、文档落盘操作）→ 自行做出合理默认，用一句话作为“可被纠偏的提案”说明选择与理由并继续推进。**凡由你自行拍板的事项，写入 Spec 时必须标注为工程默认取舍，不得伪装成用户钦定要求。**
- **审批即提问**：方案拍板、复述确认与最终 Spec 审批均通过提问工具执行（批准 / 需修改并在“其他”说明）。仔细阅读用户回答附带的补充备注，其中往往包含最核心的隐含约束。

## 3. 首条回复与渐进对齐（Alignment & Playback）

### 首条回复怎么写
- **用户已给出较具体的诉求、草稿或背景**（整段控制在 200 字左右）：
  1. 用你自己的话复述其目标、对象与已知动机，让用户一眼看出你是否抓准了轮廓；
  2. 补充代码库事实接地结论：现有相关机制怎么跑、改动会碰哪里、是否有潜在冲突或更简捷路径（此时只谈事实与约束，不急着展开具体怎么写代码）；
  3. 留一句话欢迎随时纠偏，随后针对**最能改变构建结果的那一个未决问题**调用提问工具（若尚不知动机，优先问动机；若完全无悬念且仅有一条合理路径，直接附精简方案与轻量 Spec 请用户审批）。
- **用户只给了模糊方向**：围绕最大的未决分水岭发一个开放式问题，点明不同答案会导向怎样不同的系统形态。
- **轻量退出通道**：若用户并未显式点名调用本流程或要求设计对齐，可在首问末项附一个轻量跳出选项（如“直接按常规流程实现——跳过前置追问”）；若用户选中，用一句话声明关键技术取舍后即结束本流程。

### 对齐心智地图（覆盖领域，切忌当成审讯清单逐条背诵）
- 变更的核心定位、触发契机与成功判据；
- **目标（Goals）**、**非目标（Non-Goals）**与**反目标（Anti-Goals：即便代码跑通也算工程失败的红线，如产生双份事实源、破坏工作区隔离、泄漏凭据等）**；
- 现有系统真实状态、过往尝试与用户最在意的交互/数据边界。

### 渐进复述（Play It Back）与抛弃式探针（Spike）
- **边问边复述**：仅当需求横跨多个独立切面，或用户回答明显推翻既有理解时触发切面复述确认（约 200–300 字；涉及界面、流程或结构时配简短文本草图），明确区分“用户原意”与“你补充的工程提案”，用提问工具确认无误后再推进下一块。若用户首条输入已涵盖核心动机与关键边界，只针对剩余 1–2 个真正会改变实现走向的分水岭发问并直接收敛，不为走形式强拆多轮复述。
- **抛弃式 Spike**：当某个技术可行性或体验细节靠讨论不如试跑一轮清楚时，可提议做一个快速抛弃式探针（Spike）。经用户同意的 Spike 不写正式测试、不走计划与审查流程，只为把实验事实带回对话；**若决定保留 Spike 成果转入正式交付，视为新请求，必须重新走完 Spec 与 Plan 门禁。**

---

## 4. 方案比选门禁（Approaches Gate）

在对齐“做什么与为什么”之后、动笔写正式 Spec 之前，**若存在实质技术路线分歧，必须用单独一轮回复呈现实现方案比选**：

1. 基于代码库现状构思多种真实可行的构建路径，主动淘汰违背初衷或与现有架构硬冲突的弱方案；
2. 将剩余 **2–3 个有效方案**具象化（各自改动哪些核心模块、数据/控制流怎么走、各自的工程代价与收益）；
3. 明确给出你的首选推荐及理由，通过提问工具请用户选定。若事实接地后确实只有唯一合理路径（**严禁为凑数编造稻草人方案**），无需硬拆单独比选轮次，在进入 Spec 或轻量 Spec 草案中用 2–3 句话说明为何其余思路不通即可（若用户已明确把“怎么做”全权交给你，同样声明采用推荐方案并进入写 Spec 阶段）。

## 5. 规模定级、编写 Spec 与出口交接

方案锁定后，向用户明确说明任务体量定级（用户可覆盖）：

| 规模定级 | 适用特征 | Spec 产出与复核要求 |
| :--- | :--- | :--- |
| **轻量变更（Small Change）** | 边界单一、跨模块耦合低的小型特性或行为调整 | 编写精简版 Spec（各核心维度 1–2 句话固化共识与选定方案），免除子代理盲审，直接交用户审批 |
| **完整工程（Project）** | 跨模块改造、新子系统、复杂状态流或持久化契约变更 | 读取 [spec-and-builder-check.md](./spec-and-builder-check.md)，编写完整 Spec，并在提交用户前先完成独立 **Builder Check** |

- 若任务中途范围明显膨胀，停下告知用户并升级为完整工程；若实为多个彼此独立的子项目，拆清先后顺序逐个推进。
- **落盘位置**：默认保存至 `docs/specs/YYYY-MM-DD-<topic>-design.md`（若修改对象属于被 `.gitignore` 忽略的本地工具或非软件目录，选定不污染主仓库历史的合理位置或会话产物并说明；用户指定路径优先）。
- **Builder Check（仅完整工程）**：按 [spec-and-builder-check.md](./spec-and-builder-check.md) 派发无历史上下文偏见的全新子代理（无子代理能力时切换构建者视角自行盲审）挑出“规划者不得不瞎猜且猜错会返工”的缺口。将发现的问题分三类处理：
  - *代码或前文已答* → 直接补入 Spec；
  - *次要工程细节* → 自行拍板并在 Spec 中标明为工程默认；
  - *仅用户能拍板的产品/范围分歧* → 汇总为**至多一轮**提问工具确认并更新 Spec，随后连同你做出的工程默认清单一起交用户终审。
- **审批封板与交接**：通过提问工具请用户批准 Spec。获批后：
  1. 将 Spec 顶部的状态字段更新为 `已批准（YYYY-MM-DD）`；
  2. 若项目为 Git 仓库、目标路径未被 `.gitignore` 忽略且符合仓库提交规范，按规范提交或说明文件状态；
  3. 给出 Spec 文件链接，并用一句话说明该规格已锁定，随时可在下一条指令中通过 `ask-plan` 阶段（[ask-plan.md](./ask-plan.md)）转化为增量实施计划。

<HARD-GATE>
在用户明确批准设计规格（Spec）之前，严禁开展任何构建与实现动作——包括编写或修改业务代码、新建脚手架、安装依赖、改动构建配置，以及跳步进入 ask-plan 阶段或任何实现动作。只读代码调研与经用户明确同意的抛弃式 Spike 不受此限。

两种例外：用户主动选择跳过前置追问通道时，本流程连同门禁一并结束；经同意的抛弃式 Spike 仅作实验验证，若需保留其代码必须重新回到本门禁。

用户批准 Spec 即标志着 ask 阶段彻底结束——批准 Spec 绝不自动启动规划或编码，后续进入 ask-plan 阶段或实现必须由用户的下一条明确指令触发。
</HARD-GATE>

## 常见反模式对照表（Red Flags）

| 危险念头 | 事实纠偏 |
| :--- | :--- |
| “我先列个功能菜单让用户勾想要什么” | 预设选项会绑架早期思路；摸清动机前先用开放式提问让用户自己描述。 |
| “这个问题很简单，直接在回复末尾文字问一句就行” | 每一次提问与审批都必须走结构化提问工具，且每次只问一题。 |
| “为了省轮次，我一次把四个问题全塞进提问框” | 除 Builder Check 终审收尾外一律单步追问，后一问必须建立在前一答之上。 |
| “代码太长先不看了，直接问用户现在怎么实现的” | 严禁把仓库里能查到的事实抛给用户；开口前先做代码与依赖事实接地。 |
| “这些默认取舍很合理，我默默填进设计就行” | 合理默认必须大声说出来并在 Spec 标明归属；没说出口的默认等于剥夺了用户的否决权。 |
| “问题都聊清楚了，我直接把 Spec 写出来吧” | 存在多条可行路线时，写 Spec 前必须先单独呈现 2–3 个方案及权衡供拍板；若确为唯一合理路径，须简述其余思路为何不通，严禁硬凑稻草人方案。 |
| “用户刚说‘这想法不错’，说明设计已经批了” | 审批只覆盖用户亲眼见到的具体文档；未落盘、未标记批准的 Spec 不算过门禁。 |
| “Spike 原型跑通了，干脆接着往正式功能改” | Spike 产物默认抛弃；想转正必须作为新需求重新过 Spec 与 Plan 门禁。 |
| “Spec 已经批准了，我顺手把代码或计划一起干了吧” | 批准 Spec 即结束 `ask` 阶段；进入 `ask-plan` 或编码是用户的下一条指令。 |
